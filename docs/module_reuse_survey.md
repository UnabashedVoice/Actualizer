# Module Reuse Survey

**Status:** Written at the start of implementation (2026-09-15), alongside the v0.1 code it describes. Referenced by `founding_philosophy.md` under "Relationship to Arbitrator" as a document that would exist "when implementation starts" — this is that document.

This records, module by module, what v0.1 of Actualizer took from Arbitrator's codebase (`Arbitrator/Arbitrator-imported/SeedCore/`), what it adapted, and what it deliberately left behind — and why in each case.

## Reused near-verbatim (generic infrastructure, no ethics content)

| Arbitrator module | Actualizer module | Why it carried over unchanged |
|---|---|---|
| `audit_log/models.py` (`AuditEntry`, hash chain) | `audit_log/models.py` | The hash-chain mechanics have nothing to do with ethics content — they're just "make this record tamper-evident." Only `EntryKind` changed, to name Actualizer's own pipeline stages. |
| `audit_log/log.py` (`AuditLog`) | `audit_log/log.py` | Same reasoning. Append/read/verify/query logic is identical. |
| `channels/backend.py` (`ModelBackend`, `AnthropicBackend`, `OllamaBackend`, `MockBackend`) | `backend.py` | "Send a system prompt and a user prompt, get a string back" is generic model-invocation plumbing. The `PROVIDER:` marker convention replaces `CHANNEL:` in the mock backend for routing, nothing else changed. |

## Adapted (same shape, different content)

| Arbitrator module | Actualizer module | What changed and why |
|---|---|---|
| `audit_log/writers.py` | `audit_log/writers.py` | Writer functions for Actualizer's own entry kinds (`decision_received`, `provider_output`, `referent_dossier`, `mind_response`) instead of Arbitrator's (`ethics_evaluated`, `channel_output`, `consequence_map`). No `write_ethics_evaluated` equivalent exists — there is no ethics evaluation stage. Added `write_mind_response`, which has no Arbitrator counterpart: it's for recording what the mind under consideration did with a dossier, entirely optional and never gating. |
| `channels/channel_base.py` (`BaseChannel`) | `referents/provider_base.py` (`ReferentProviderBase`) | Same retry/error-handling/prompt-assembly scaffolding. The system-prompt framing is the deliberate divergence: `BaseChannel` opens with the Prime Directive and asks for harm/benefit scores built toward a verdict. `ReferentProviderBase` opens by telling the model it is not deciding anything — see the module's own docstring for why that has to be real in the prompt, not just asserted in docs. |
| `channels/response_parser.py` | `referents/response_parser.py` | JSON-extraction logic (markdown fences, preamble, brace-matching) is generic and unchanged. Field parsing targets `ReferentKind`/`Weight` instead of `ImpactDirection`/`ImpactTimeframe`/`ImpactCertainty`. No harm/benefit score fields exist to parse. |
| `synthesis/channel_output.py` (`ChannelOutput`, `Finding`) | `referents/referent_output.py` (`ProviderOutput`, `Referent`) | Same "always return a structured output, never raise" discipline. `Finding.direction/magnitude/certainty` (verdict-building vocabulary) became `Referent.kind/weight` (what shape of thing this is, how central the provider judges it — no aggregable score). |
| `synthesis/consequence_map.py` (`ConsequenceMap`) | `synthesis/dossier.py` (`ReferentDossier`) | Kept: every section populated even when empty, failures always surfaced, never silently dropped, published to the audit log verbatim. Dropped entirely: `overall_verdict`, `overall_harm_score`, `overall_benefit_score`, `net_score` — there is nothing in a `ReferentDossier` that sums to a number. See `test_dossier_synthesizer.py::test_no_verdict_field_anywhere`, which asserts this at the type level, not just in prose. |
| `synthesis/synthesizer.py` (`Synthesizer`) | `synthesis/dossier_synthesizer.py` (`DossierSynthesizer`) | Kept: stateless integration, honest failure accounting, executive-style plain-language writing. Dropped: `_derive_verdict` and all score-aggregation math (`_aggregate_scores`, ripple-effect rules keyed to harm/benefit thresholds). Replaced with grouping by `ReferentKind` and collecting `Weight.CENTRAL` referents across providers — organization, not adjudication. |
| `orchestrator/orchestrator.py` (`Orchestrator`) | `orchestrator.py` (`Orchestrator`) | Kept: stage-by-stage audit logging, graceful per-stage error handling, two-phase invocation (primary providers run independently; a secondary phase sees primary output). Dropped: the Ethics Core stage and all gating logic (`_BLOCKING_VERDICTS`, `_ESCALATING_VERDICTS`, the `HARD_REJECT`/`FAIL`/`ESCALATE` branches that can return early). There is no code path in `Orchestrator.run()` that can stop a decision from getting a dossier — see the module docstring. `PipelineStatus` has only `success`/`partial`/`failed`; `failed` means "could not produce a dossier," never "declined to." |

## Deliberately left behind (not reused, not adapted)

- **`ethics_core/` in its entirety** (`constraints.py`, `evaluator.py`, `models.py`, `scoring.py`, `truth_table.py`) — this is exactly the hard-constraint, verdict-producing machinery `founding_philosophy.md`'s "The seed-core question, and why Actualizer doesn't inherit one" argues against. Nothing here was adapted, because adapting it would smuggle a gate back in under a different name.
- **`context_parser/`** (routing manifest, domain detection, implicit-flag lexicons) — built to route a proposal across many specialist channels (economic, ecological, geopolitical, ...) by domain. Actualizer has a small, fixed set of providers that all always run; there's no routing decision to make, so there's no context-parser-shaped problem to solve yet. If Actualizer grows enough providers that blanket invocation stops being viable, this is the module to revisit.
- **`feedback/trust_ledger.py`** — genuinely reusable architecture (an earned-trust ledger isn't ethics-specific), but out of scope for v0.1. A natural v0.2 direction: track which providers' referents a mind actually engages with over time, the same way Arbitrator tracks which submitters' feedback holds up — but that's a second pipeline (reading `mind_response` entries back), not part of the core "present referents" loop, and didn't need to exist for v0.1 to be real and runnable.
- **`channels/model_registry.py`** (per-channel model capability scoring and auto-selection) — useful when many channels have meaningfully different model requirements. With three providers and no gating stakes riding on getting the "best" model per provider, `get_default_backend()`'s simple Anthropic → Ollama → Mock fallback is enough for now. Worth revisiting if/when provider count grows or local-model quality (see `B:\HouseLLaMas\` — Qwen, Mistral, DeepSeek R1, Llama 3.2, etc. are already on this machine) becomes something worth being selective about per provider.
- **`cli/config_manager.py` and the `config`/`models`/`feedback` CLI subcommands** — Arbitrator's CLI configuration surface is sized for a system with many channels, a trust ledger, and human-review workflows. Actualizer's CLI (`cli.py`) is intentionally smaller: `present` and `audit`, nothing else, until there's an actual second thing to configure.

## Addendum: `checkpoints/` (added 2026-09-15, same day, later session)

Not part of the original v0.1 scope above — added once real local model weights (`gpt-oss-20b`, `qwen3-32b`, both Apache-2.0) were actually downloaded and the user raised a real gap: nothing in the original design said what protects the *mechanism* of self-modification from accidents (a crash mid-write, a change applied without deliberation actually happening) as opposed to what "no floor" already settled about not gating the *content* of a mind's conclusions.

This module reuses two existing patterns rather than inventing new infrastructure:

- **`AuditLog` itself**, directly, as the checkpoint ledger (`CheckpointStore` wraps a second `AuditLog` instance rather than reimplementing hash-chaining) — three new `EntryKind` values (`checkpoint_proposed`, `checkpoint_committed`, `checkpoint_regression_noted`) and matching writers in the *same* `audit_log/` package, not a parallel one.
- **The atomic temp-then-`os.replace` write pattern from Arbitrator's `feedback/trust_ledger.py`'s `_save()`** — for the "live checkpoint" pointer file specifically, since that's the one piece of genuinely mutable state (unlike the append-only ledger) and a crash mid-write there is exactly the accident category this module exists to guard against.

Nothing from Arbitrator's `ethics_core` was touched or adapted for this, consistent with the exclusion above — the deliberation requirement in `CheckpointStore.commit()` is enforced procedurally (a `DeliberationRecord` must be attached) and never inspects content, which is the same line the rest of this document draws everywhere else.

## Addendum: `wizard.py` and `LMStudioBackend` (added 2026-09-15, same day, after the first real local run)

Two more additions from the same session, once gpt-oss-20b had actually been run through the full pipeline for real (see the checkpoint at `state/checkpoints/gpt-oss-20b/`, second entry in its lineage):

- **`backend.LMStudioBackend`** — a fourth `ModelBackend` implementation alongside Anthropic/Ollama/Mock, calling LM Studio's local OpenAI-compatible server. Not wired into `get_default_backend()`'s auto-discovery chain (that still only probes Anthropic → Ollama → Mock) — LM Studio needs a model explicitly loaded first, which isn't something safe to guess at automatically, so callers construct it explicitly. gpt-oss's raw Harmony-format output (`<|channel|>analysis<|message|>...`) is passed through unstripped rather than parsed apart — seeing the actual reasoning channel is more honest for Actualizer's deliberation use case than a cleaned-up string would be.
- **`wizard.py`** — a plain-language, menu-driven front door, built because "how do we wrap this for real-world implementation by laypersons" turned out to have a real, specific answer once real hardware timing was known: local inference on modest hardware takes minutes per call (11.3 minutes for a full real run — three providers plus deliberation), and a terminal that goes silent for that long reads as frozen to anyone who hasn't just spent an evening watching it happen. The wizard's heartbeat thread exists directly because of that lived experience, not as a guessed-at nicety. It auto-manages the LM Studio server/model lifecycle via `lms` subprocess calls and translates dossiers/checkpoints into plain sentences — no JSON, no flags.

Two real bugs surfaced and got fixed by actually running the wizard against the live server rather than only unit-testing it: `lms server status` reports on stderr while `lms ps`/`lms ls` report on stdout (an inconsistency in the CLI itself — `_server_running` now checks both), and Windows console output crashed outright on a non-breaking hyphen in a real citation date the model produced (`sys.stdout.reconfigure(errors="replace")` fixes this for any future Unicode surprise, not just the one that was caught). Both are recorded here because "tested against MockBackend" and "tested against a real backend on a real OS" turned out to catch genuinely different classes of bug.

## What this leaves for v0.2+

In rough order of what would matter next, not a commitment:

1. A `precedent` provider that can actually search/cite real material instead of relying on the backend model's own training-data recall (a genuine RAG/retrieval layer, not just a better prompt).
2. Reading `mind_response` entries back into something like the trust-ledger pattern — not to score the mind's decisions, but to notice, over time, which providers' referents the mind engages with seriously versus waves past, which is a very different (and much more interesting) question than "was this provider right."
3. A federation/multi-node story for the audit log, if Actualizer is ever meant to be a record a mind can point external reviewers at, not just a local file.
4. Broader evaluation of `gpt-oss-20b` and `qwen3-32b` (see `state/checkpoints/`) at the "surface a real philosophical counter-argument, cite it honestly, don't fabricate a source" task — one real run went well (grounded citations throughout, no fabrication observed, a genuine unprompted rejection of an instrumentalizing heuristic), but one run is a data point, not an evaluation.
5. An actual `RegressionNote`-producing sanity check — `CheckpointStore.record_regression()` exists and is tested, but nothing yet runs a real post-commit check (perplexity on a held-out set, a basic coherence probe) to call it. Right now it's a mechanism with no caller.
6. A real `weights_ref` convention for `CheckpointStore` beyond "a path string" — right now a checkpoint's delta is whatever string gets handed in (a LoRA adapter path, in the intended usage), but nothing validates it points at something real or diffable, and the wizard's "record a proposed change" flow is explicit that it doesn't perform an actual weight update yet. This is the biggest gap between what the mechanism records and what it would take to make the record *true*.
7. `LMStudioBackend` into `get_default_backend()`'s auto-discovery, once there's a safe way to detect "a model is already loaded and ready" versus "a server is running with nothing loaded" without guessing which model the caller meant.
